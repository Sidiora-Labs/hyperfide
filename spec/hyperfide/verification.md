# Hyperfide verification and qualification plan

Status: **DRAFT — implementation approval required. All product acceptance cases below are UNRUN.**

This document proposes the qualification contract for Hyperfide, the Codify 2.0 successor. It specifies work to implement after approval. It records no successful product, provider, model, load, or recovery qualification. Authoring and reviewing this specification pack is a separate activity.

The public qualification target uses frontier coding agents, 48–72-hour runs, at least 200 concurrent remote agents in the large-run profile, 100 combined sandboxes, semantic as well as mechanical assurance, and a main server dedicated to supervision. The endurance profile covers up to 1,500 session lifetimes. Smaller profiles have separate declared concurrency targets. These are proposed qualification targets, not claims about existing account entitlements or achieved capacity.

## 1. Evidence rules

1. A case passes only when its observable invariant holds against identified executable inputs. Source inspection, a model opinion, process exit, dashboard status, grep match, or a task's `done` field cannot alone prove runtime correctness.
2. Evidence identifies spec revision, requirement/criterion IDs, case ID, runner revision, source commit set, environment/preparation digest, graph version when relevant, input fixture digests, random seed, policy configuration, model/connector versions where applicable, and observed outcome. Record expected and actual assertions, not merely a boolean summary.
3. Evidence includes invocation, UTC start/end, monotonic durations, exit status, complete stdout/stderr artifact references and hashes, injected fault schedule, event trace, and relevant externally observed effects. Secrets must be redacted before durable publication; redaction must preserve the ability to prove outcomes using non-secret identifiers.
4. Every acceptance case starts `UNRUN`. Results become `PASS`, `FAIL`, or `BLOCKED` only after an actual attempt. A missing credential, unsupported provider capability, unavailable service, or absent fixture is `BLOCKED` with nonzero gate status, never an implicit pass. A required case cannot be waived through an unrecorded skip.
5. Evidence is append-only. Re-execution creates a new result. Changed relevant inputs invalidate reuse while preserving historical results. Task qualification, integrated-candidate qualification, wave closure, and programme closure have separate evidence objects.
6. An independent checker reconstructs accepted ownership, publication, and coverage from durable records plus observable Git/provider effects. It must not trust the same handler's success response as its sole oracle.
7. Timing checks use monotonic clocks. Clock skew is injected; lease expiry and publication authority must follow the authoritative contract, not a worker's wall clock.
8. The harness operates in disposable projects, databases, repositories, and provider resources. Record every created resource. Teardown must be verified from provider inventory and durable state; attempted deletion is insufficient.

## 2. Planned harness interface

The following paths and commands are **planned interfaces to implement**, not existing working tools:

```text
python3 tests/hyperfide/qualify.py --case V-001 --manifest <immutable-campaign-manifest.json>
python3 tests/hyperfide/qualify.py --task N.M --manifest <immutable-campaign-manifest.json>
python3 tests/hyperfide/qualify.py --suite <registered-suite> --manifest <immutable-campaign-manifest.json>
python3 tests/hyperfide/qualify.py --list-cases --format json
python3 tests/hyperfide/check-evidence.py --campaign <campaign-result-directory>
python3 tests/hyperfide/selftest_harness.py
```

The runner must fail nonzero if the runner or required checker is absent; selector is missing, empty, unknown or resolves to zero cases; case IDs are duplicated; a declared assertion is unexecuted; expected artifacts are missing; a fixture/credential is absent; infrastructure setup fails; a child process times out; or cleanup cannot be established. It must not implement `try import ... except: pass`, optional-command success fallbacks, or grep-only acceptance. Every required suite declares the exact case list and expected assertion count. The independent evidence checker rejects mismatches. A partial result must never be printed as complete qualification.

Registered suites are proposed as `contract`, `storage-graph`, `provider-railway`, `provider-blaxel`, `native-agents`, `assurance`, `compatibility`, `deterministic-load`, `live-canary`, `live-soak`, and `release`. Provider cases must run once for each required provider; connector cases once per required connector/authentication route. A case can belong to several suites, but one execution cannot claim a distinct untested provider or connector.

A native task command uses `--case V-NNN --manifest tests/hyperfide/manifests/tasks/N.M.json`. The immutable manifest selects an explicitly registered component variant containing exact assertion IDs, parent V-case identities, prerequisites, inputs and expected assertion counts. No new variant CLI flag or implicit narrowing is permitted. The optional convenience interface `--task N.M` resolves exactly that same registered task-manifest entry; it cannot infer selectors or waive assertions. A narrow stage-appropriate behavioural probe can qualify a bounded foundation task without requiring its later live infrastructure. That task result cannot mark its parent end-to-end V-case PASS. Full V-case qualification requires every required subassertion and provider/connector variant. Each receipt declares `task-component`, `full-case`, or `campaign` scope and exact executed assertion inventory. A component PASS cannot set its parent V-case or whole acceptance clause PASS. The independent checker compares the declared full inventory with all current receipts; missing fragments/counts/variants or evidence from an unrelated provider remain incomplete. Unknown tasks, probes, prerequisites or zero selected probes fail nonzero. Results report task/probe coverage separately from product-case coverage.

`selftest_harness.py` is the planned bootstrap executable, implemented with standard-library test facilities and temporary child executables. It must genuinely exercise runner selection, execution, failure propagation, timeout, assertion accounting and evidence validation using controlled successful/failing processes. It needs no cloud, frontier calls or product database. Missing runner implementation, unknown/empty selectors, zero assertions, absent required files, failed children and malformed/partial artifacts are negative tests whose rejection is asserted; merely grepping the runner source cannot pass this bootstrap gate.

For native KVX task verification, use selected `--case` invocations or registered suites with a manifest. Do not substitute Markdown existence checks for these product gates. Shell/Python reporting code must propagate subprocess failures and timeouts. Campaign manifests resolve paths, approved resources and permitted actions explicitly; a product harness must refuse to provision real resources unless that campaign is explicitly approved.

First 48-hour campaign, then 72-hour campaign, with 1,500 session lifetimes in the 72-hour run. | V-050–V-052 pass at declared hardware/account/model profiles. | S7 — release rehearsal | Run migration, main restart, DB failover, provider loss, stop/cleanup, backup restore, documentation closure and release rollback against the release candidate. | V-053–V-056 plus all applicable prior cases pass with current evidence; no unresolved blocking finding; leader receives a complete closure packet. |

Stage numbering orders campaigns, not implementation waves. Early task components may exercise versioned deterministic provider/model fixtures or standalone native authentication probes without claiming live behavior. A live provider/model/connector variant must be explicitly selected and approved, must run its actual required resources, and returns BLOCKED if credentials or capacity are absent. It cannot fall back to a simulator. Authentication transport integration follows task13.1, and actual 48/72-hour renewal evidence follows task27.3. Cutover/rollback rehearsal task25.2 consumes the naming/client transition and precedes expensive fleet endurance.

Stage numbering orders campaigns, not implementation waves. A task may implement a harness earlier, but cannot claim a later live result from a simulator. Failed stages preserve evidence and return work to accountable managers. Re-enter a stage after relevant fixes and rerun affected dependent cases.
