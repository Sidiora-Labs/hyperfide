## نظرة عامة

Codify (ويُستدعى بالأمر `cg`) هو محرك سير عمل للوكلاء في ملف تنفيذي واحد. يتولى الأشياء الأربعة التي يحتاجها المشروع فيما وراء الشيفرة نفسها — ما **هي** الشيفرة، وكيف وصلت إلى **هنا**، وما الذي سيحدث **تاليًا**، وما الذي جرى **تعلّمه** في الطريق — ويقدّم الأربعة جميعًا للبشر ولوكلاء الذكاء الاصطناعي على حد سواء.

**ما هي الشيفرة.** يفهرس Codify تسع عشرة لغة في رسم بياني قابل للاستعلام: الرموز، وحواف الاستدعاء، ومسارات واعية بأطر العمل، وبحث نصي كامل فوري، وكل ذلك مخزَّن محليًا في SQLite. يجيب `cg context <query>` عن سؤال «أطلعني على هذه المنطقة» في استدعاء واحد: نقاط الدخول، والرموز المطابقة مع مقتطفاتها، والمستدعون، والمستدعَون، والمسارات ذات الصلة.

**كيف وصلت إلى هنا.** نظام لقطات مدمج مُعنوَن بالمحتوى يمنحك الالتزامات والتاريخ والفروق والاستعادة دون الحاجة إلى أي نظام تحكم بالإصدارات خارجي. ولأن اللقطات تتشارك قاعدة البيانات نفسها مع الرسم البياني، يقدّم `cg changes` تقريرًا عن نطاق أثر تعديلاتك غير الملتزم بها، ويكتب `cg changelog` ملاحظات إصدار على مستوى الرموز من تلقاء نفسه.

**ما الذي سيحدث تاليًا.** يحوّل محرك المواصفات ملفات kvx النصية العادية إلى خطة عمل فعلية: لوحة مهام بموجات اعتماد، وانضباط مهمة واحدة قيد التنفيذ في كل مرة، ومعايير قبول مرفقة بكل مهمة — وحالة `done` مُتحقَّق منها لا مُدّعاة. يجب أن تنجح فحوص المهمة، وأن توجد الرموز والملفات التي تدّعي تسليمها موجودة فعلًا في الرسم البياني وفي التاريخ، قبل أن يضعها Codify مكتملة.

**ما الذي جرى تعلّمه في الطريق.** تخزّن ذاكرة الوكيل ملاحظات مقصودة — قرارات وقيودًا ونتائج وتفضيلات وحقائق — في قاعدة البيانات نفسها التي يعيش فيها الرسم البياني، مرتبطةً بالمهمة التي كُتبت في أثنائها. يحفظ `cg remember` ملاحظة في منتصف المهمة، ويسجّل كل `cg spec done` نتيجة صادقة تلقائيًا (بما في ذلك حالات الرفض)، ويعيد `cg recall` كل ذلك مرتَّبًا حسب الصلة والحداثة.

الطبقات يعزز بعضها بعضًا: تُوسم الالتزامات تلقائيًا بالمهمة التي تنفذها، وتظهر الذكريات على المهمة التي تنتمي إليها، ويسير `cg spec trace` من أي مهمة إلى رموزها والتزاماتها وذكرياتها، ويوفّر خادم MCP مدمج كل ذلك — 17 أداة — لـ Claude Code وCursor وكل وكيل آخر يدعم MCP.

لا مفاتيح API، ولا خدمات تعمل في الخلفية، ولا قياس عن بُعد. كل شيء يعمل على جهازك ويبقى فيه.

## لماذا Codify

**يغلق الحلقة من الخطة إلى الإثبات.** معظم الأدوات إما تخطط العمل (قوائم مهام) أو تصف الشيفرة (بحث وفهارس). أما Codify فيفعل الأمرين على قاعدة البيانات نفسها، فيمكن التحقق من الخطة مقابل الواقع: عندما تعلن مهمة أنها تُدخل `checkMode` وتمسّ `src/*.ts`، يرفض `cg spec done` وضعها مكتملة حتى يتفق الرسم البياني والتاريخ على ذلك.

**الوكلاء يعملون كالمهندسين لا كالسائحين.** بدلًا من التجول في المستودع ملفًا تلو الآخر، يسأل الوكيل `cg spec next` عمّا يجب فعله، و`cg context` عن كل ما يخص المنطقة، و`cg impact` عمّن سينكسر — ثم يلتزم مع إسناد المهمة تلقائيًا. الحلقة بأكملها متاحة عبر MCP، فلا يضطر أبدًا إلى مغادرة البروتوكول.

**المشروع يتذكر ما تنساه الجلسات.** نوافذ سياق الوكلاء تُصفَّر؛ أما جدول الذاكرة فلا. قرار كُتب مرة واحدة بـ `cg remember` يلاقي الجلسة التالية تلقائيًا — عند `cg spec next`، وعند `cg spec start`، وفي `cg recall` في بداية الجلسة — بدلًا من إعادة اكتشافه بكامل التكلفة. ولأن حالات الإكمال المرفوضة تُسجَّل أيضًا، فإن «هذه المهمة أُعيقت مرتين وهذا هو السبب» على بُعد استعلام واحد.

**السياق يصل في استدعاء واحد، لا عشرين.** صُمم `cg context <query>` حول الطريقة التي يستهلك بها الوكلاء الشيفرة فعليًا. طلب واحد يعيد كل ما يلزم لبدء العمل: من أين يدخل التنفيذ، وما الذي تطابق، ومن يستدعيه، وما الذي يستدعيه، وأي المسارات تمسّه.

**تحليل الأثر أمر من الدرجة الأولى.** يسير `cg impact <name> -d 3` عبر حواف المستدعِين والمستدعَين بشكل متعدٍّ ويجيب عن السؤالين الأهم قبل أي تغيير: من سينكسر إذا تغيّر هذا، وعلامَ يعتمد.

**البحث فوري ومتعدد الطبقات.** فهرس FTS5 ثلاثي الحروف على أسماء الرموز يوفر مطابقة سلاسل جزئية غير حساسة لحالة الأحرف دون أي إحماء، ويسانده فهرس كلمات على كامل محتوى الملفات لكل ما عدا ذلك.

**الفهرس لا يتقادم أبدًا.** يستمع `cg watch` إلى أحداث نظام التشغيل الأصلية (inotify على Linux، وFSEvents على macOS، وReadDirectoryChangesW على Windows، وكلها خلف طبقة منصة واحدة) ويزامن تلقائيًا مع إزالة الارتداد. كما تجري استدعاءات أدوات MCP مزامنة قبل القراءة، فيستعلم الوكيل المتصل دائمًا عن بيانات حديثة.

**يتكيف مع العتاد الذي يعمل عليه.** عند البدء، يحدد `cg` حجم مجموعة العمّال وذاكرات SQLite المؤقتة بناءً على ما يوفره النظام فعليًا: عدد أنوية واعٍ بالحاويات (تقاطع حصة CPU في cgroup v1/v2 مع قناع الارتباط ومع الأنوية المتاحة)، وذاكرة متاحة حقيقية (تقاطع `MemAvailable` مع حدود ذاكرة cgroup)، وتكلفة مقيسة لكل مشروع. محطة عمل بـ 16 نواة تحصل على خط الأنابيب المتوازي الكامل، بينما يحصل خادم VPS بنواتين على خط مضبوط لينهي عمله بموثوقية. شغِّل `cg info` لترى بالضبط كيف جرى تحديد حجم خط الأنابيب.

**كل شيء يبقى محليًا.** يعيش الرسم البياني في قاعدة بيانات SQLite تحت المجلد `.codegraph/`، واللقطات كائنات مُعنوَنة بالمحتوى تحت `.codegraph/objects/`. احذف المجلد وسيختفي كل أثر.

## جلسة واحدة مع Codify

```sh
cg recall auth                # ما قررته الجلسات السابقة بشأن هذه المنطقة
cg spec next                  # المهمة المؤهلة التالية، مع معايير قبولها والذكريات ذات الصلة
cg spec start 16.7            # احجزها — مهمة واحدة قيد التنفيذ في كل مرة
cg context "password auth"    # نقاط الدخول والرموز والمستدعون والمسارات في استدعاء واحد
cg impact verifyLogin -d 2    # من سينكسر إذا تغيّر هذا
# ...نفّذ التغيير...
cg remember "sessions rotate on login" --type decision   # مرتبطة بالمهمة 16.7
cg commit -m "add password auth"   # لقطة موسومة تلقائيًا [spec:ion_spec/16.7]
cg spec done 16.7             # يشغّل verify_cmd + فحوص الرسم البياني، وتُسجَّل ذكرى نتيجة
cg spec trace 16.7            # الإثبات: المهمة -> الرموز -> الالتزامات -> الذكريات
```

كل أمر في تلك الحلقة هو أيضًا أداة MCP، فيستطيع وكيل متصل تشغيلها من البداية إلى النهاية — وكل خطوة تعمل في مشروع من عشرة ملفات بالكفاءة نفسها التي تعمل بها في مستودع ضخم موحّد.

## التثبيت

‏Linux x86_64 — أمر واحد يثبّت (أو يحدّث) ملفًا تنفيذيًا ساكنًا متحقَّقًا منه عبر checksum:

```sh
curl -fsSL https://codify.centra.ag/install | bash
```

لإزالة التثبيت: `curl -fsSL https://codify.centra.ag/uninstall | bash`. بيانات `.codegraph/` الخاصة بكل مشروع لا تُمَس أبدًا.

على المنصات الأخرى، ابنِ من المصدر (المتطلبات: مترجم C و`libsqlite3-dev`):

```sh
make && sudo make install
```

ثم في أي مشروع:

```sh
cd your-project
cg init
```

## مرجع الأوامر

### الرسم البياني

| الأمر | الوصف |
|---|---|
| `cg init` | ينشئ `.codegraph/` ويبني الفهرس الأولي |
| `cg sync` / `cg index [--full]` | إعادة فهرسة تدريجية أو كاملة |
| `cg search <q> [-n N]` | بحث في الرموز وبحث نصي كامل |
| `cg symbol <name>` | التعريف والمقتطف وعدد المراجع |
| `cg impact <name> [-d N]` | المستدعون والمستدعَون بشكل متعدٍّ |
| `cg context <q>` | حزمة سياق باستدعاء واحد للوكلاء |
| `cg routes [filter]` | جدول من نمط URL إلى المعالج |
| `cg watch [--debounce MS]` | مزامنة تلقائية عند أحداث نظام الملفات الأصلية |
| `cg info` | ملف تعريف الجهاز وتقرير تحديد حجم خط الأنابيب |

### التحكم بالإصدارات

اللقطات مُعنوَنة بالمحتوى باستخدام SHA-256 مع إزالة تكرار الكتل.

| الأمر | الوصف |
|---|---|
| `cg commit -m <msg>` | يلتقط لقطة لشجرة العمل |
| `cg log` / `cg status` | التاريخ، وحالة شجرة العمل مقابل HEAD |
| `cg diff [A] [B]` | فرق أسطر LCS بين اللقطات أو مع شجرة العمل |
| `cg checkout <id> [--force]` | يستعيد لقطة |
| `cg changes` | نطاق أثر التعديلات غير الملتزم بها: الرموز التي لمستها إضافة إلى مستدعيها الخارجيين |

### الذاكرة

ملاحظات وكيل دائمة، مخزَّنة في قاعدة بيانات SQLite نفسها مع الرسم البياني. الذكريات المكتوبة أثناء وجود مهمة spec قيد التنفيذ تربط نفسها بها، ويسجّل `cg spec done` النتائج تلقائيًا. لا تخزّن فيها الأسرار أبدًا.

| الأمر | الوصف |
|---|---|
| `cg remember <text>` | يحفظ ذكرى — `--type decision\|constraint\|outcome\|preference\|fact` (الافتراضي `fact`)، و`--task <feature/id>` (يفترض افتراضيًا مهمة spec الجارية)، ومرتكزات اختيارية عبر `--symbols` / `--files` |
| `cg recall [query]` | يبحث في الذكريات: بحث نصي كامل في المحتوى، مرتَّبًا حسب الصلة ثم الحداثة؛ ويمكن الترشيح بـ `--task` و`--type` و`-n N` |
| `cg forget <id>` | يحذف ذكرى |

### للوكلاء

| الأمر | الوصف |
|---|---|
| `cg mcp` | يعمل كخادم MCP عبر stdio بـ 17 أداة: search وcontext وsymbol وimpact وroutes وstatus وchange-impact وlog وcommit وأدوات spec (status وnext وstart وdone وrender وtrace) والذاكرة (remember وrecall) |
| `cg mcp-install` | اتصال تلقائي بـ Claude Code (عبر `.mcp.json`) وCursor وVS Code وWindsurf وGemini CLI وCodex CLI مع الدمج في الإعدادات القائمة |
| `cg changelog [-n N] [-o FILE]` | سجل تغييرات من اللقطات مع فروق على مستوى الرمز: دوال مضافة ومحذوفة ومسارات جديدة |
| `cg agentmd [--write]` | يولّد `AGENTS.md` و`CLAUDE.md`: اللغات وخريطة المجلدات وأدوات البناء ونقاط الدخول والمسارات والرموز الأكثر إشارة إليها |

جميع أوامر الاستعلام تقبل `--json`. هذا الخيار مع خادم MCP يشكّلان الواجهة المصممة للوكلاء.

## سير عمل المواصفات (Spec)

سير عمل المواصفات هو الطريقة التي يحوّل بها Codify خطة ميزة إلى عمل متتبَّع ومُتحقَّق منه. تعيش المواصفات كملفات kvx نصية عادية — يقرؤها البشر، وتقبل المقارنة، ويملكها مستودعك — ويصيّرها Codify إلى ملفات قواعد لبيئات التطوير ومرايا markdown بينما يدير حلقة المهام فوقها. يعمل في أي مستودع يحتوي على `spec/workflow.kvx`، وهو مستقل تمامًا عن `.codegraph/`، وبديل مباشر بلغة C عن `spec/specgen` الخاص بـ Ion بمخرجات متطابقة بايتًا ببايت.

| الأمر | الوصف |
|---|---|
| `cg spec render [--check]` | يعيد توليد ملفات المؤشر الخاصة ببيئات التطوير (Cursor وDevin وClaude وCodex وCopilot وKiro) ومرآة markdown (الملفات `requirements.md` و`design.md` و`tasks.md`)؛ ويخرج `--check` بالرمز 2 إذا كان أي شيء قديمًا |
| `cg spec` / `cg spec status` | لوحة المهام: الأعداد والتقدم والمهمة الجارية حاليًا والمهمة المؤهلة التالية |
| `cg spec next` | المهمة المعلّقة ذات أدنى موجة التي اكتملت جميع متطلباتها في `requires`، مع نقاط تنفيذها ومعايير قبولها الموسّعة |
| `cg spec start <id>` | يضع المهمة في حالة `in_progress`؛ يفرض مهمة واحدة في كل مرة واستيفاء `requires`، ويمكن تجاوز ذلك بـ `--force` |
| `cg spec done <id>` | يشغّل `verify_cmd` الخاص بالمهمة وفحوص الرسم البياني (يرفض عند الفشل، ويتجاوز `--force` ذلك)، ثم يضعها في حالة `done` ويسجّل ذكرى نتيجة ويقترح المهمة التالية |
| `cg spec trace [<id>]` | يتتبع المهام إلى الشيفرة: الرموز المعلنة محلولة في الرسم البياني (الموقع والنوع والمراجع)، والمسارات الملموسة مطابَقة مع التغييرات الفعلية، والالتزامات الموسومة بالمهمة، وذكرياتها |

يعيد `start` و`done` كتابة سطر واحد فقط هو `status = "..."` في ملف kvx. كل بايت وتعليق وسطر فارغ آخر يبقى كما هو. بعد ذلك يعيد الأمر التصيير بهدوء لتبقى مربعات الاختيار في `tasks.md` محدثة. تظل ملفات kvx مصدر الحقيقة الوحيد، ويتيح `-f <feature>` تجاوز `[meta] active_feature`.

يضيف `cg commit` تلقائيًا وسم المهمة الجارية إلى رسالته، مثل `... [spec:ion_spec/16.7]`، وبذلك يتتبع `cg log` و`cg changelog` كل لقطة رجوعًا إلى المواصفة. كما أن أوامر spec الستة متاحة أيضًا كأدوات MCP، فيستطيع الوكيل المتصل إدارة الدورة كاملة (next ثم start ثم التنفيذ ثم done) دون مغادرة البروتوكول.

وعندما يمتلك المشروع أيضًا فهرس `.codegraph/`، يمكن للمهام أن تعلن الشكل الذي يبدو عليه تنفيذها، ويتحقق `cg spec done` من ذلك مقابل الواقع:

```ini
[task.2.1]
title   = "Check mode"
symbols = ["checkMode"]      # يجب أن يوجد في الرسم البياني للشيفرة
touches = ["src/*.ts"]       # يجب أن يكون مسار مطابق قد تغيّر فعلًا
```

تُبحث `symbols` في الرسم البياني المفهرس؛ وتُطابق أنماط `touches` (مسارات دقيقة أو أنماط glob) مع اتحاد تغييرات شجرة العمل والملفات التي غيّرتها الالتزامات الموسومة بالمهمة — وبذلك يظل التحقق ناجحًا حتى بعد الالتزام بالعمل. الفحوص الفاشلة ترفض الإكمال (ويتجاوزها `--force`). ويعرض `cg spec trace [<id>]` سلسلة المهمة ثم الشيفرة ثم الالتزام كاملة لمهمة واحدة أو للميزة بأكملها، نصيًا أو بـ `--json`.

كما يغذّي سير العمل طبقة الذاكرة من تلقاء نفسه. كل إكمال يكتب ذكرى نتيجة موجزة — بما في ذلك حالات الرفض، ليتسنى لجلسة لاحقة أن ترى أن مهمة ما أُعيقت ولماذا. ويطبع `cg spec next` و`cg spec start` الذكريات ذات الصلة بالمهمة (المرتبطة بمعرّفها، أو المطابقة لعنوانها)، ويضمّنها `cg spec trace` في السلسلة. الوكيل الذي يدير الحلقة يبني ذاكرة المشروع دون أن يُطلب منه ذلك أبدًا.

## امتداد VS Code

يحتوي `editors/vscode/` على امتداد Codify: تمييز صياغة لملفات المواصفات `.kvx`، إضافة إلى لوحة مهام حيّة في المستكشف — مهام مجمّعة حسب موجة الاعتماديات مع أيقونات حالة، وبيانات التحقق من الرسم البياني خلف كل مهمة (الرموز ومواقعها، المسارات المتأثرة، الإيداعات الموسومة)، وإجراءات بدء/إكمال تنفّذ أوامر `cg spec` الحقيقية (بما في ذلك الرفض عند فشل الفحوص)، ومؤشر تقدّم في شريط الحالة. يستدعي الامتداد `cg` ولا يحتاج إلى أي خطوة بناء:

```sh
cd editors/vscode
npx @vscode/vsce package        # ينتج codify-0.1.0.vsix
code --install-extension codify-0.1.0.vsix
```

انظر [editors/vscode/README.md](../../editors/vscode/README.md).

## التطوير

```sh
make             # يبني ./cg              (المتطلبات: مصرِّف C وlibsqlite3-dev)
make unit        # اختبارات وحدات C       (tests/unit/*.c مقابل build/libcg.a)
make integration # اختبارات CLI شاملة     (tests/integration/*.sh داخل بيئات معزولة)
make test        # كلاهما
```

بنية المستودع:

```
src/                 ملف .c واحد لكل وحدة؛ src/cg.h هو الترويسة الوحيدة
tests/unit/          قواعد kvx ومتجهات SHA-256 وماسح JSON وStrBuf/IO
tests/integration/   الرسم البياني وvcs والوكلاء وبروتوكول MCP ومحرك spec والمراقب
tests/fixtures/      مشروع متعدد اللغات نموذجي ومستودع spec بمخرجات ذهبية
editors/vscode/      امتداد VS Code: لغة kvx + لوحة المهام (JS خالص)
docs/ARCHITECTURE.md كيف تتكامل الأجزاء
```

المخرجات الذهبية لتصيير المواصفات وُلِّدت بواسطة specgen الأصلي المكتوب بلغة Go، وبذلك يضمن `make test` تطابق التصيير. تبني بيئة CI وتشغّل مجموعة الاختبارات الكاملة عند كل دفعة عبر `.github/workflows/ci.yml`.

## ملاحظات وحدود

- تجمع قواعد التجاهل بين قيم افتراضية معقولة (مجلدات VCS و`node_modules` ومخرجات البناء والملفات الثنائية) وملف `.cgignore` بنمط glob واحد في كل سطر.
- استخراج الرموز استدلالي. محرك أنماط لكل لغة، واعٍ بالتعليقات والسلاسل النصية، مضبوط لتحقيق أعلى استرجاع ممكن للتعريفات ومواضع الاستدعاء. وهو ليس محلِّلًا كاملًا مدققًا للأنواع.
- تخزّن اللقطات كل ملف غير مُتجاهَل حتى 32 ميغابايت، بما في ذلك الملفات الثنائية. ويفهرس الرسم البياني الملفات النصية حتى 8 ميغابايت.
