# Contributing to Codify

Thanks for taking the time to contribute. This document explains how the project is organized, what we expect from patches, and how to get changes merged quickly.

## Ground rules

- Be respectful. The [code of conduct](CODE_OF_CONDUCT.md) applies to every interaction in this project.
- Keep changes focused. One pull request should do one thing. If you find yourself fixing an unrelated bug on the way, split it out.
- Every change that touches behavior needs a test. If it can't be tested, explain why in the PR description.
- Discuss large changes first. Open an issue before writing a thousand lines nobody asked for. Small fixes and obvious improvements can go straight to a PR.

## Getting set up

You need a C compiler (GCC or Clang), `make`, and `libsqlite3-dev`.

```sh
git clone https://github.com/sidiora-labs/codify.git
cd codify
make            # builds ./cg
make test       # unit + integration suites
```

If `make test` passes on a clean checkout, your environment is fine.

## Project layout

The codebase is deliberately flat: one `.c` file per module, and `src/cg.h` is the only header. Before adding a new file, check whether the change belongs in an existing module. Read `docs/ARCHITECTURE.md` before touching anything structural.

```
src/                 modules; src/cg.h is the single shared header
tests/unit/          C unit tests linked against build/libcg.a
tests/integration/   shell-based end-to-end tests, each run in a sandbox
tests/fixtures/      sample polyglot project and a spec repo with golden outputs
```

## Coding standards

- **C11 with the project's GNU/POSIX environment.** The Makefile builds with `-std=gnu11`, `-Wall`, and `-Wextra`. Keep compiler warnings actionable; do not assume the current implementation is strict ISO C without extensions.
- **No new dependencies.** SQLite is the only external library, and that is intentional. If your change needs another library, open an issue first; the answer will usually be no.
- **Match the surrounding style.** Look at the module you are editing and follow it. Consistency inside a file beats personal preference.
- **Memory discipline.** Every allocation has an owner and a clear free path. Run your changes under `valgrind` or ASan before submitting.
- **Error handling.** Library functions return status codes and never call `exit()`. Only the CLI entry points in `main.c` are allowed to terminate the process.

## Tests

- Unit tests live in `tests/unit/` and cover pure logic: the kvx grammar, SHA-256 vectors, the JSON scanner, StrBuf and IO helpers. Add one whenever you touch these areas.
- Integration tests live in `tests/integration/` as shell scripts that run the real `cg` binary in temporary repositories. These directories isolate test data; they are not an operating-system security sandbox. If your change alters CLI output or behavior, add or update a script there.
- Spec rendering is locked to golden outputs generated by the original Go specgen. If your change legitimately alters the rendered output, regenerate the goldens and explain the difference in the PR. Byte-identical parity is a feature, so this bar is high.

Run everything before pushing:

```sh
make test
"$PWD/cg" spec render --check
"$PWD/cg" spec lint
"$PWD/cg" check
```

Use the checkout binary, not a potentially older `cg` on PATH. To run the documentation feature's focused tests, use `CG="$PWD/cg" tests/integration/24_docs.sh`. `make release` publishes to the configured web root; it is not a local-only test command.

## Documentation is part of completion

When all implementation tasks have qualified, an enabled feature exposes `@docs`. Follow the [documentation workflow](docs/DOCUMENTATION.md) to update user guidance, developer guidance, and release/migration notes through the existing connector or an interactive session. Keep unrelated human material intact and finish with `cg docs close`, which checks the evidence and records the documentation snapshot.

The [source reference](docs/SOURCE-REFERENCE.md) is a navigation index of implementation declarations, not a supported public API list. [Test and fixture observations](docs/TEST-REFERENCE.md) are intentionally separate. Consult [the architecture guide](docs/ARCHITECTURE.md) for module responsibilities and behavioral contracts.

## Adding language or framework support

Language extractors are heuristic pattern engines, tuned for recall on definitions and call sites. A new language needs:

1. A language-table entry in `src/lang.c`, aware of that language's comment and string syntax; extend the shared extractor only where the syntax requires it.
2. A fixture in `tests/fixtures/` with representative definitions, calls, and edge cases.
3. An integration test verifying symbols and edges land in the graph.

Framework route support follows the same shape: patterns, fixture, integration test.

## Commit messages

Write in the imperative mood with a short summary line, a blank line, and a body when the change needs explanation:

```
watcher: debounce rename storms on Linux

inotify delivers MOVED_FROM/MOVED_TO as separate events, which caused
double syncs during large refactors. Coalesce pairs within the debounce
window before scheduling a sync.
```

Reference issues with `Fixes #123` where applicable.

## Pull request process

1. Fork, branch from `main`, and make your change.
2. Run `make test` and confirm everything passes.
3. Open a PR with a clear description: what changed, why, and how you verified it.
4. A maintainer will review. Expect requests for changes; that is normal and not a rejection.
5. Once approved, a maintainer merges. We use squash merges, so your PR title becomes the commit summary. Make it a good one.

CI runs the full suite on every push. A red CI means the PR will not be reviewed until it is green.

## Reporting bugs

Open an issue with:

- The output of `cg info` (it includes the machine profile and version).
- Exact steps to reproduce, ideally against `tests/fixtures/` or a minimal public repo.
- What you expected and what actually happened.

For anything security-sensitive, do not open a public issue. Follow the [security policy](SECURITY.md) instead.
